## Supuestos funcionales

La historia no cuantifica “frecuente”. Se aplican los supuestos solicitados:

- Al menos dos pedidos distintos en estado `entregado`, del mismo agricultor,
  que contienen el producto y cuya **fecha_pedido** está entre NOW() - 90 días y NOW(),
  incluidos los extremos. La ventana mide fecha de compra, no fecha de entrega real.
- Se usa `COUNT(DISTINCT p.id_pedido)`; varias líneas de un pedido no son varias compras.
  Las compras pueden pertenecer a distintos distribuidores del mismo producto.
- Baja estricta del precio persistido del mismo inventario, producto activo y stock positivo.
- Seguidores manuales siguen calificando sin compras frecuentes; la unión se deduplica
  por id_agricultor. No se insertan filas en producto_seguido automáticamente.
- Descuento: `(anterior - nuevo) / anterior * 100`, redondeado a dos decimales.
- No hay Firebase nuevo, índices, migraciones ni dependencias nuevas.

## Flujo

1. PUT de inventario bloquea la fila, lee su precio anterior, actualiza y confirma.
   POST también puede cambiar precios mediante upsert: bloquea el distribuidor para
   serializar publicaciones simultáneas y la fila existente de inventario.
2. Después del COMMIT se libera la conexión. Solo una baja con stock positivo llama
   a PrecioNotificacionService. Errores de avisos no revierten la actualización.
3. Se consulta el producto activo una vez; seguidores y compradores frecuentes se
   consultan una vez cada uno. Se deduplican destinatarios. Se conserva el envío en
   lotes de hasta 10 inserciones concurrentes, sin búsquedas de producto por destinatario.
4. NotificacionService persiste `BAJA_PRECIO` / `baja_precio` con el JSON compatible:
   id_producto, producto, precio_anterior, precio_nuevo, porcentaje_descuento.
   Fallos individuales se registran sin mensajes internos o credenciales; no hay
   reintentos automáticos que recreen avisos ya exitosos.
5. GET /api/notifications resuelve el perfil a partir del JWT y filtra por propietario.
   PATCH /api/notifications/:id/read verifica también propiedad en el UPDATE.
6. Android comparte AppNotification/NotificationContent y métodos Retrofit de
   notificaciones. PriceNotificationViewModel carga únicamente para agricultores,
   descarta solicitudes de carga obsoletas y limpia datos al cambiar de usuario.
7. Home muestra alertas no leídas con nombre, ambos precios y descuento; tocar la
   tarjeta abre ProductDetail del ID recibido. Un botón separado marca como leída
   mediante PATCH y la elimina al confirmar éxito. Un resultado viejo de GET no
   restaura IDs marcados durante la sesión. Carga/error/reintento son locales a la
   sección de alertas; el resto de Home sigue visible. Distribuidores conservan sus
   avisos urgentes, sin mostrar tarjetas baja_precio.

## Consulta para KAN-107

Archivo: `backend/src/repositories/CompraFrecuenteRepository.js`.
Parámetro $1: ID de producto, resuelto en servidor. Medir con datos representativos
mediante EXPLAIN (ANALYZE, BUFFERS): cardinalidades, tiempo, lecturas y costo de
JOIN/GROUP BY/COUNT(DISTINCT). No se agregaron índices especulativos.

```sql
SELECT p.id_agricultor
       FROM pedido p
       JOIN detalle_pedido d ON d.id_pedido = p.id_pedido
       JOIN inventario_distribuidor i ON i.id_inventario = d.id_inventario
       WHERE i.id_producto = $1
         AND p.estado = 'entregado'
         AND p.fecha_pedido >= NOW() - INTERVAL '90 days'
         AND p.fecha_pedido <= NOW()
       GROUP BY p.id_agricultor
       HAVING COUNT(DISTINCT p.id_pedido) >= 2
```

## Validación visual y limitaciones

El 2026-10-11 el usuario confirmó que la interfaz se ve bien en Android Studio y
autorizó publicar el PR. Se preparó el emulador y una compilación apuntando al backend
local temporal. El agente no completó personalmente el recorrido visual de extremo
a extremo; no se atribuye esa validación a las pruebas automatizadas. Existen pruebas
Compose de contenido y callbacks, ViewModel de sesión/red/lectura y HTTP con PostgreSQL real.

Lista de comprobación funcional manual para revisión: iniciar sesión con agricultor que tenga dos pedidos
entregados recientes; bajar precio de inventario con stock; verificar un único aviso;
abrir el producto; volver y marcar como leído; recargar Home y confirmar que no vuelve;
repetir con agricultor no frecuente/no seguidor (sin aviso), con seguidor manual
(aviso) y con distribuidor (conservar urgente, sin baja_precio).

Se conserva el mecanismo de entrega posterior al commit existente, sin outbox ni
reintentos duraderos: una caída del proceso o fallo de inserción puede perder un aviso.
La deduplicación cubre destinatarios del mismo cambio, no un nuevo sistema de entrega
exactamente una vez. La sección consulta al entrar a Home y al reintentar; no es push.
Los precios representan el evento almacenado, no una garantía de disponibilidad futura.

La interfaz tiene confirmación visual del usuario. El recorrido funcional manual completo
no fue confirmado paso a paso; permanece como lista de revisión. Los dos fallos
preexistentes de la batería general quedaron corregidos y verificados.
