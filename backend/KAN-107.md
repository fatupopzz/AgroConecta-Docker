# KAN-107 — Índices SQL con evidencia local

Implementación en `feature/KAN-107-sql-indexes`, basada en `origin/develop` `ec79766`.
KAN-102 integrada mediante [PR #99](https://github.com/fatupopzz/AgroConecta-Docker/pull/99).
No se reescribieron consultas, respuestas, autorizaciones ni rutas. No hay extensiones nuevas.

## Método y alcance

PostgreSQL 15 en Docker local con datos exclusivamente sintéticos, almacenamiento tmpfs y semilla `setseed(0.107)`.
Se inspeccionaron controladores de productos, pedidos, inventario, distribuidores, reseñas y notificaciones;
repositorios de seguidores y compradores frecuentes, rutas, restricciones e índices.
La selección de endpoints se basa en el flujo del producto; no hay telemetría real para afirmar cuáles son los más usados.
`benchmark.cjs` extrae las consultas literales del código y sustituye únicamente las interpolaciones de las variantes medidas.
Los JSON guardan SQL y parámetros exactos. Una ejecución de calentamiento y cinco medidas por consulta;
las tablas muestran medianas. `ANALYZE` antes de cada fase; no se deshabilitaron planes secuenciales ni se forzaron índices.
La base final se creó de nuevo para excluir residuos de las pruebas exploratorias de escritura y se ejecutó `VACUUM ANALYZE`.
La línea base retira solo los índices KAN-107 dentro de una transacción que termina en ROLLBACK; conserva todos los índices previos.
No hay carga concurrente de prueba en las cifras finales de lectura. Es una medición de caché caliente, no una prueba de disco ni de concurrencia.
Los planes completos incluyen planificación, ejecución, filas estimadas/reales por nodo, loops, filtros, buffers y temporales.

Cardinalidades: `usuario` 21,001, `agricultor` 20,000, `distribuidor` 1,000, `producto` 10,000, `inventario_distribuidor` 100,000, `pedido` 200,000, `detalle_pedido` 800,000, `resena` 98,411, `producto_seguido` 20,000, `notificacion` 200,000.

Hay cinco categorías, 90% de productos activos, 80% de distribuidores verificados, 60% de pedidos entregados,
fechas de compra distribuidas en 365 días, 5% de pedidos urgentes y cuatro detalles por pedido.
Cada distribuidor ofrece 100 productos. El producto 1 aparece en todos los distribuidores y en aproximadamente un tercio de los pedidos;
se miden tanto ese caso como el producto 74, mucho menos frecuente. Las fechas se fijan respecto a NOW al sembrar;
la misma base se utiliza en ambas fases. La muestra no reproduce estadísticas de producción, geografía, textos reales,
clientes concurrentes, caché fría ni distribución completa de tamaños por agricultor. No garantiza porcentajes de mejora en Azure.

## Aporte individual y descartes

En cada prueba se elimina temporalmente **un solo candidato** en una transacción y se revierte al terminar.
Los demás índices permanecen. Así se evita atribuir toda una mejora a un índice que no contribuye.

I1: el listado por categoría varía y una tanda fue más lenta; por eso se midió también el endpoint completo
(conteo + listado), alternando con/sin índice en la misma sesión. Tras dos pares de calentamiento, diez pares:
**36.755 ms sin I1 → 34.465 ms con I1**. Es una mejora modesta, no la eliminación del orden aleatorio.

Se descartó **conservar la combinación inicial de ocho índices sin I9**: en la exploración perjudicaba el producto popular
por miles de búsquedas en `pedido_pkey`. La prueba final de retiro de I9 confirma el problema;
I9 permite un Index Only Scan del rango de entregados y un Hash Join en ese caso.
El producto 74 puede devolver cero compradores frecuentes; el producto popular sí genera destinatarios y evita validar solo el caso vacío.

No se propusieron índices nuevos para:

- Inventario por distribuidor: el UNIQUE `(id_distribuidor,id_producto)` ya filtra; el orden también utiliza nombre de producto de otra tabla.
- Distribuidores verificados/nombre: baja selectividad (80%) y costo dominante de agregación global de reseñas; no se demostró necesidad de otro índice.
- Seguidores: `idx_producto_seguido_producto` ya filtra. No se añadió otro para ahorrar un sort de dos filas.
- Notificaciones de agricultor: `idx_notificacion_agricultor_fecha` ya cubre el patrón.
- Búsqueda `ILIKE '%texto%'`, `LOWER(CONCAT_WS(...))` en recomendaciones y `ORDER BY RANDOM()`: un B-tree normal de nombre no resuelve esos patrones.
  Se midió ILIKE; las recomendaciones se inspeccionaron estáticamente, sin afirmar una mejora para ellas. No se agregaron extensiones ni se cambió el comportamiento.

No se duplicaron PRIMARY KEY/UNIQUE de usuario, agricultor, distribuidor, inventario, pago, producto_seguido y reseñas.
Los catálogos de índices y restricciones están en la evidencia. Se detectó que el índice existente
`idx_producto_seguido_agricultor_producto` ya duplica el UNIQUE de esas columnas; se dejó intacto.
No se eliminaron índices existentes del proyecto. Los DROP de los scripts afectan solo candidatos propios en la base desechable y se revierten.

## Escrituras

Seis tandas con rollback, primera descartada. Lotes de 1 000 productos/inventarios/pedidos, 4 000 detalles;
actualizaciones de 1 000 filas. Las pruebas usan EXPLAIN ANALYZE con WAL, ejecutan realmente el DML y lo revierten.
No se confunde rollback con ausencia de costo de escritura. Las secuencias pueden avanzar en la base desechable.
Los tiempos dependen de caché, FK, vacuum y asignación de páginas; los bytes WAL muestran el costo adicional más claramente.

| Operación | ms antes → después | WAL bytes antes → después |
|---|---:|---:|
| insert_product | 6.625 → 8.544 | 168143 → 232685 |
| insert_inventory | 31.067 → 30.930 | 222554 → 300690 |
| insert_orders | 29.268 → 30.444 | 176250 → 362866 |
| insert_details | 109.918 → 122.684 | 600339 → 1.1939e+06 |
| update_product | 10.187 → 10.146 | 461328 → 516450 |
| update_inventory | 9.307 → 12.065 | 305198 → 390990 |
| update_orders | 6.512 → 16.722 | 258928 → 504212 |

Los índices añaden trabajo a INSERT/DELETE y a UPDATE de sus columnas/predicados; pueden impedir actualizaciones HOT.
I9 indexa solo entregados, pero cambiar el estado de un pedido puede insertar/eliminar su entrada. La migración no cambia reglas de negocio ni constraints.

## Aplicación recomendada en producción (no ejecutada)

La migración entregada usa CREATE INDEX normal: bloquea escrituras de la tabla durante la construcción.
Para tablas en uso, preparar una copia revisada con `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, ejecutar cada sentencia
fuera de una transacción y serializar las creaciones por tabla. Consume más trabajo/tiempo y puede esperar transacciones activas.
Revisar espacio, carga, definición existente y `pg_index.indisvalid`; IF NOT EXISTS solo compara nombres y no verifica equivalencia.
Si falla una construcción concurrente puede quedar un índice inválido: investigar y acordar recuperación, sin borrado automático.
Después ejecutar ANALYZE y repetir las consultas con parámetros/distribuciones reales, supervisando también latencia de escritura.
[Documentación oficial PostgreSQL 15](https://www.postgresql.org/docs/15/sql-createindex.html).

Ejemplo de sintaxis para **uno** de los índices, a usar solo en una conexión de despliegue previamente autorizada:

```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_kan107_detalle_pedido_orden
    ON detalle_pedido (id_pedido, id_detalle);
ANALYZE detalle_pedido;
```

No ejecutar init.sql completo sobre producción para desplegar estos índices.

## Reproducción y archivos

Desde el repositorio: `bash backend/benchmarks/kan107/run.sh`.
Requiere Docker y acceso a las imágenes/dependencias del proyecto. El script crea su propio contenedor PostgreSQL 15 sin puertos publicados,
lo detiene al finalizar y conserva evidencia en la carpeta temporal que imprime. No usa bases configuradas por .env ni volúmenes existentes.
La semilla rechaza una base con nombre distinto de kan107_benchmark o productos preexistentes.
Se necesita memoria suficiente para tmpfs y aproximadamente un millón de filas relacionadas.

- `sql/kan107_sql_indexes_migration.sql`: nueve índices idempotentes con comentarios de consultas.
- `sql/init.sql`: las mismas definiciones para instalaciones nuevas.
- `benchmarks/kan107/`: semilla, extractor de consultas, mediciones, retiro individual, costo de escritura, pruebas HTTP y validador de migración.
- `benchmarks/kan107/evidence/*.json.gz`: planes completos, catálogos, restricciones, respuestas sintéticas y resultados.
  Leer con `gzip -dc backend/benchmarks/kan107/evidence/before.json.gz` (o cualquier lector gzip).
- Este informe: metodología, resultados, decisiones y limitaciones.
